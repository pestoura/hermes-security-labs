## 3. Problem and motivation

Playbooks and results are internal formats, preventing exchange with external tooling, governance systems and partners.

## 4. Intended outcome

Import and export mappings for recognised interchange formats covering playbooks, results and control assessments.

## 5. Scope and non-goals

### In scope

- Playbook interchange mapping
- Result and finding export mapping
- Control assessment export mapping
- Round-trip fidelity rules
- Explicit target schema identity/version
- Data markings and signature-verification evidence on export envelopes

### Non-goals

- Claiming certified conformance with any interchange standard
- Treating imported or interchanged content as execution authorization
- Fetching authoritative schemas or activating external integrations in this repository block

## 6. Intent architecture

Internal models remain canonical; interchange formats are projections with documented lossy fields. Interchange data is descriptive and portable data only: imported content never grants authorization, expands scope or makes a step executable. Hermes / Control Plane remains the sole authority that may issue execution authorization.

## 7. Contracts, data and capabilities

Repository implementation introduced by PR #157 is under `platform/interoperability/`:

- `export-envelope.schema.json`;
- `interoperability-policy.yaml`;
- `interoperability.py`;
- repository tests in `platform/tests/test_interoperability.py`.

The contract supports these format identifiers:

- `oscal-assessment-results`;
- `oscal-poam`;
- `cacao-2.0`;
- `attack-flow`.

For every envelope, the repository contract requires:

- exact target schema identifier;
- exact target schema version;
- an explicitly supplied target JSON Schema;
- payload validation against that supplied schema using JSON Schema Draft 2020-12;
- one or more explicit data markings;
- externally supplied evidence asserting a verified signature, including signer and algorithm metadata;
- deterministic canonical payload SHA-256.

The repository does **not** cryptographically verify or create a document signature in this block. Signature evidence is an input gate, not proof generated by the interoperability component itself.

Contracts are canonical in Git. Where this epic reuses a platform-wide contract, the canonical definition lives in the [reference architecture](../../architecture/security-validation-reference-architecture.md) and in [EPIC-01](EPIC-01-architecture-and-canonical-contracts.md); this document references it instead of restating it.

## 9. Security, risks and failure modes

- Silent information loss on export
- Standard version drift
- Caller supplying an incompatible or misleading target schema
- Treating signature metadata as cryptographic proof generated by this component
- Treating imported playbooks as authorization or executable instructions
- Exporting data without markings

Platform-wide invariants that this epic must not weaken:

- absence of evidence never produces a `PASS` verdict;
- no execution outside an active authorization contract;
- **Hermes / Control Plane remains the sole execution-authorization authority**;
- imported content never grants authorization, expands authorization or creates an `authorization_ref`;
- no secrets, tokens, cookies or raw credential material in documentation, telemetry or persisted evidence;
- no target outside registered laboratories;
- unsupported formats, invalid schemas, incompatible payloads, missing markings or unverified signature evidence fail closed.

## 10. Deliverables

Repository candidate delivered by PR #157:

- interoperability export-envelope schema;
- interoperability policy;
- deterministic export builder and target-schema validator;
- format allowlist for OSCAL Assessment Results, OSCAL POA&M, CACAO 2.0 and Attack Flow;

Still pending:

- governed authoritative schema acquisition/version lifecycle;
- concrete internal-to-standard mapping completeness/lossiness model;
- cryptographic signing and verification integration;
- external transport/delivery;
- consumer integration and interoperability round-trip tests;
- certified conformance, which is not claimed.

## 11. Acceptance criteria

Repository-level evidence currently demonstrates:

- supported export envelopes validate their payload against the explicitly supplied target schema;
- target schema identity/version are recorded;
- missing data markings fail closed;
- unverified signature evidence fails closed;
- payload SHA-256 is deterministic.

Epic/umbrella acceptance still requires operational evidence that:

- mappings are complete enough for the declared supported fields and document lossy fields;
- governed target schemas are used rather than arbitrary caller-selected schema substitutes;
- exported documents are signed/verified by the designated cryptographic component;
- external consumers accept supported exports;
- supported-field round-trip behaviour is demonstrated and stable.

## 13. Decisions and open questions

### Decisions

- Interchange formats never become the internal source of truth.
- Imported or interchanged content never grants execution authorization.
- Hermes / Control Plane remains the sole execution-authorization authority.
- An explicitly supplied schema is sufficient for the repository contract candidate, but not for a claim of authoritative/certified interoperability.
- Verified-signature evidence is required by the envelope contract; cryptographic signing itself belongs to a separate operational integration.
- Unknown or invalid format/schema/payload conditions fail closed.

### Open questions

- Authoritative schema acquisition, pinning and deprecation policy per format
- Exact lossiness/mapping inventory for each supported standard object
- Cryptographic signer/verifier component and trust policy
- External transport and consumer authentication model
- Round-trip compatibility scope and fixtures
